3Exactly-Once Submission ADR

PayEx decision record, incl. "Where the agent was wrong or useless" (R2)

Problem statement

How do you guarantee an approved invoice reaches PayEx exactly once? Compare at least three options (idempotency key + dedupe table, transactional outbox + worker, optimistic submission + nightly reconciliation), lay out the trade-offs, then stress it three ways: state a preference for a different option and see if the recommendation moves; ask how it fails at 3 a.m. on the last day of the month; ask what it costs to build and to run. Write the record with a "what would make me revisit this" section and a "Where the agent was wrong or useless" section. Account for: PayEx times out at 30s and a timeout doesn't mean failure; Service Bus is provisioned but unused; SOC 2 needs a 7-year audit trail.

What we did

  • Three options each scored on 30s-timeout behaviour, behaviour at ~80 approvals/min at month-end, build cost, run cost, and dominant failure mode.
  • Decision: transactional outbox + worker, with an idempotency key carried to PayEx — keeps the 30s call off the request path (the INC-2041 lesson) and makes ambiguous timeouts a visible needs_reconciliation state.
  • Stress test 1 — preferred Option C; recommendation held, with the one condition that would move it.
  • Stress test 2 — 3 a.m. failure answered via INC-2047's silent-worker pattern (filter mismatch, 200s while nothing is submitted).
  • Stress test 3 — build vs run cost stated, build cost named as the strongest counter-argument.
  • Revisit triggers (6) and a candid "Where the agent was wrong or useless" section (unverified PayEx contract, hand-wavy costs, missing worker-sizing math).
Recorded decision: transactional outbox + worker + idempotency key, adopted for the January release — with the monitoring (outbox-age alerting) treated as part of the decision, not optional.
